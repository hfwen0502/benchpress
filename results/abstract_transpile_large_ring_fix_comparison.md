# Abstract Transpile Large: Ring/Chain Fix Comparison

Comparing Qiskit 2.3.1 (baseline) vs our ring/chain-aware fix on the QASMBench Large suite (58 circuits x 4 topologies = 232 tests). Both built from source with `--release`, measured on the same remote Linux server (160 vCPUs), `optimization_level=2`.

## Summary

| Metric | Value |
|--------|------:|
| Total tests | 232 |
| Total baseline time | 1,388s |
| Total fix time | 1,342s |
| Overall speedup | 1.03x |
| Tests with >1.5x speedup | 0 |
| Tests with >10% gate change | 18 (noise) |

**Conclusion**: Our fix has no meaningful impact on the abstract transpile large suite. The gate count variations are within SABRE's stochastic noise (both positive and negative). This is expected — the abstract transpile creates a `FlexibleBackend` sized to each circuit's qubit count, so none of these tests trigger the odd-ring-on-bipartite-hardware scenario that our fix targets. The fix is specifically effective for **device transpile** (fixed larger backend, ring/chain circuits with VF2 timeout).
